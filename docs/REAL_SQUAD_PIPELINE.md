# 실제 스쿼드 기반 명단과 초상 — 계획과 파이프라인

2026-09-04 결정. 목표는 "현실감": 각 리그 20클럽의 실제 스쿼드를 카드로
만들고, 선수마다 실사풍 초상을 붙인다. 이름과 클럽은 지금처럼 가명이고,
실명은 운영자 화면에서만 본다(`rosterRealHints.ts`의 이중화 원칙).

## 결정 사항

| 항목 | 결정 | 이유 |
| --- | --- | --- |
| 초상 방식 | **속성 기반 가상 실사** — 사진 없이 국적·나이·포지션 체격·(키에서 뽑은) 머리·수염·표정으로 생성 | 실제 사진을 참고한 닮은꼴은 초상권·퍼블리시티권·소스 저작권 위험이 크다. 현실감은 거의 같고 특정인과 닮지 않는다 |
| 첫 범위 | 1클럽(울산 호랑, 33명) 시범 → 검토 후 확장 | 데이터·가명·초상·표시까지 한 번 끝까지 돌려 본 뒤 규모를 키운다 |
| 기존 카드 | 같은 클럽·포지션의 새 카드로 자동 이관(레벨·경험치 유지) | 컬렉션이 새 명단으로 이어진다. 매핑 규칙은 아래 |
| 데이터 | 공개 자료(위키백과 스쿼드 표)에서 수집, 능력치는 규칙으로 생성 후 선수편집 탭에서 보정 | 사용자가 보유한 데이터가 있으면 그 형식에 맞춰 스크립트를 바꾼다 |

## 파이프라인

```
data/squads/<club>.json           실명·등번호·포지션·국적·생년·종합 (운영자 자료)
   │  npm run build:squads
   ▼
lib/rosterSquads.ts               SQUAD_ROSTER(가명 행), SQUAD_REAL_HINTS(가명→실명),
                                  SQUAD_PORTRAITS(가명→초상 키), SQUAD_PORTRAIT_META
   │  lib/players.ts ROSTER 가 LATE_ADDITIONS 뒤에 붙임 → id 부여
   ▼
node scripts/portrait-prompts.mjs > prompts.jsonl      속성 → 프롬프트(JSONL)
node scripts/gen-portraits.mjs prompts.jsonl log       이미지 도구 호출, assets/players/<key>.png
npm run build:portraits                                public/players/<key>.webp(256²) + lib/portraitManifest.ts
   ▼
components/PlayerAvatar.tsx       매니페스트에 키가 있으면 <img>, 없으면 기존 SVG (요구 3번)
```

- **id는 명단 내 위치**다. 새 클럽 JSON은 파일명 정렬상 뒤에 오게 만들고,
  한 파일 안에서도 선수 순서를 바꾸지 않는다. 앞에 끼워 넣으면 뒤 카드의
  id가 밀려 모든 세이브의 컬렉션이 바뀐다.
- **`unreleased`**: JSON의 `pilot: true`면 카드가 `PLAYERS`에는 있지만
  뽑기·이적시장·합성·조각 풀(`PLAYERS_BY_RARITY`)에서 빠진다. 승인 후
  `pilot`을 지우고 다시 빌드하면 공개된다.
- 가명 규칙: 이름 한 음절만 바꾼다(조현우→조현운, 김영권→김영궁). 기존
  명단과 가명이 겹치면 빌드가 실패하므로 그때 바꾼다.
- 종합치는 실제 위상을 게임 스케일로 옮긴 추정값이다. 등급은 종합으로
  자동 배정(86+ 월드, 82+ 라이브, 76+ 레전드, 68+ 레어).
- 초상 프롬프트는 "가상의 인물이며 실존 선수·유명인과 닮지 않아야 한다"를
  명시한다. 실존 인물 사진은 어떤 단계에서도 쓰지 않는다.

## 규모와 비용 (7리그 전체 기준)

- 140클럽 × 약 25명 ≈ 3,500장. 무료 이미지 도구는 장당 60~100초라 순차로
  약 60~90시간. 유료 API로 돌리면 $70~150, 하루 안.
- 저장: 256² webp 장당 10~20KB → 3,500장 ≈ 50MB. 저장소에 두면 무거우니
  확장 단계에서는 Supabase Storage(CDN)로 옮기고 `PlayerAvatar`의 경로만
  바꾼다.

## 기존 카드 이관 (설계)

새 명단이 한 클럽에 들어오면 그 클럽의 옛 카드(생성 명단)를 새 카드로 옮긴다.

1. 후보: 같은 클럽, 같은 포지션 그룹(GK/DF/MF/FW)의 새 카드.
2. 우선순위: 같은 세부 포지션 → 종합 차이가 가장 작은 카드 → 등급이 같은 카드.
3. 유지: 레벨·한계·경험치·컨디션. 등급이 달라지면 레벨 상한(`RARITY_TIERS`)에
   맞춰 잘라낸다.
4. 매핑 표는 `lib/rosterMigration.ts`에 옛 id → 새 id 로 고정해 두고,
   세이브를 읽을 때(`lib/storage.ts` normalize)와 서버 `put_save` 양쪽에서
   같은 표를 적용한다. 서버 조각 기록(`collected`)도 함께 바꾼다.
5. 옛 카드는 명단에 남되 `unreleased`로 풀에서 빠진다(다른 유저가 아직
   들고 있을 수 있으므로 삭제하지 않는다).

시범 승인 뒤 울산 호랑의 옛 카드 24장(n02·r01·lg247… )부터 적용한다.

## 감독 카드 (차기 컨텐츠 초안)

- 감독 카드 1장을 스쿼드에 둔다. 가명·가상 초상은 선수와 같은 방식.
- 효과는 전술에 붙는다: 특기 프리셋(총공세·균형·역습·잠그기) 하나에
  보너스, 특정 포메이션 숙련, 팀 컬러 조건(같은 리그 출신)과의 시너지.
- 히든 카드처럼 경기 전 효과가 아니라 상시 효과라서 등급별 수치를 작게
  잡는다(전력 +1~+4 수준). 자동 교체 판단이나 체력 관리 같은 "감독다운"
  보정도 후보.
- 획득: 뽑기 별도 풀, 시즌 순위 보상, 경쟁 리그 컵 우승 보상.
- 필요한 설계: 카드 타입 확장(`items` 또는 별도 `managers`), 세이브 필드,
  경기 엔진의 `MatchSetup` 보정 지점, 스쿼드 탭 슬롯. 선수 명단 작업이
  자리 잡은 뒤 별도 문서로 진행.
