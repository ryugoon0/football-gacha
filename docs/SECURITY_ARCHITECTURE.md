# 신뢰 경계와 서버 권한 이전 계획

상용화와 실시간 리그를 전제로 한 보안 설계입니다. 지금 정하는 이유는 하나입니다:
**기능을 잘못된 쪽에 쌓을수록 옮기는 비용이 커집니다.** 코드는 아직 대부분
그대로지만, 앞으로 만드는 것은 이 문서의 경계를 지켜서 만듭니다.

## 1. 지금 상태 — 클라이언트가 심판이다

```
브라우저 localStorage ──(로그인 시 그대로 업로드)──> saves.data (jsonb)
   ↑ 골드·카드·전적·순위가 전부 여기서 결정된다
```

- 골드 증감은 전부 `lib/gameReducer.ts`에서 계산됩니다. 서버는 관여하지 않습니다.
- `/api/gacha`는 서버 판정처럼 보이지만 아닙니다. `GachaTab`에 로컬 폴백이 있어
  요청을 실패시키면 브라우저가 스스로 뽑고, 어차피 골드 차감과 카드 획득은
  클라이언트가 결정합니다.
- 경기 결과도 브라우저에서 시뮬레이션되므로 순위·보상·트로피가 자기 신고입니다.
- `normalizeSave`는 **모양만** 고칩니다. 골드가 99억이면 99억을 그대로 받습니다.

RLS 덕분에 **남의 데이터는 안전합니다**(`auth.uid() = user_id`). 문제는 자기
데이터를 마음대로 쓸 수 있다는 것이고, 순위·PvP·결제가 붙는 순간 그것이 곧
남의 플레이 가치를 깎는 문제로 바뀝니다.

## 2. 신뢰 경계 — 무엇을 서버가 소유해야 하는가

`GameState`의 모든 필드를 네 부류로 나눕니다. **앞으로 필드를 추가할 때 반드시
어느 부류인지 정하고 만듭니다.**

### A. 자산 (Entitlement) — 서버가 소유해야 함
`gold` · `cards` · `shards` · `capacity` · `pity` · `pulls` · `collected` · `trophies`

돈이 되거나 돈으로 살 수 있는 것. 클라이언트가 한 글자도 결정해서는 안 됩니다.

### B. 성적 (Progression) — 경쟁이 붙는 순간 서버가 소유해야 함
`season` · `cup` · `matchday` · `record` · `gf` · `ga` · `history` · `market`

혼자 하는 동안은 로컬이어도 되지만, 순위표·PvP·실시간 리그가 들어오면
공유 자원이 되므로 서버 계산이어야 합니다.

### C. 취향 (Preference) — 클라이언트가 소유해도 됨
`tactic` · `plan` · `autoSub` · `guideDone` · 카드 스타일 · 전술 방식

조작해도 본인 화면만 바뀝니다. 서버에 저장하더라도 검증할 필요가 없습니다.
단 `club`(클럽 이름)은 남에게 보이므로 **길이·욕설 필터가 필요**합니다.

### D. 선언 (Declaration) — 클라이언트가 제출하되 서버가 검증
`squad` (포메이션과 배치)

플레이어의 지시이므로 클라이언트가 정하는 게 맞습니다. 다만 서버는 "이 사람이
실제로 소유한 카드인가", "부상 중인 선수를 넣지 않았나"를 반드시 확인합니다.

### E. 파생 (Derived) — 저장하지 말고 다시 계산
`lastRatings` · `lastSubs`

서버가 경기를 계산하면 함께 나오는 값입니다. 클라이언트가 보낸 것을 믿을 이유가
전혀 없습니다.

## 3. 우리에게 있는 이점

**전술 엔진이 이미 순수 함수이고 난수 시드를 주입받습니다.** 테스트를 위해 그렇게
만들었지만, 결과적으로 서버 이전이 훨씬 쉬워졌습니다:

- `runToEnd(setup, rng)`은 같은 입력에 같은 결과를 냅니다.
- Supabase Edge Function은 Deno이므로 **`lib/matchEngine.ts`와 `lib/tactics/*`를
  그대로 가져다 쓸 수 있습니다.** 로직을 두 벌 쓰지 않아도 됩니다.
- 즉 서버가 시드를 발급하고 경기를 돌리면, 클라이언트는 같은 시드로 같은 경기를
  재생만 하면 됩니다. 관전 경험은 그대로 두고 판정만 서버로 옮길 수 있습니다.

이건 흔치 않은 출발점입니다. 보통은 엔진이 UI와 얽혀 있어 서버 이전에 재작성이
필요합니다.

## 4. 단계별 이전 계획

각 단계는 **독립적으로 배포 가능**하고, 이전 단계를 되돌리지 않습니다.

### 0단계 — 감사와 방어벽 (게임 동작 변화 없음)
- `saves`에 쓰기 감사 로그를 남깁니다. 누가 언제 무엇을 어떻게 바꿨는지 기록.
- **물리적으로 불가능한** 저장만 거부하는 트리거를 겁니다. 정상 플레이는 절대
  막지 않는 느슨한 상한이며, 목적은 차단보다 **탐지**입니다.
- 저장 쓰기 빈도 제한.

*버는 것*: 조작이 일어나면 나중에 찾아낼 수 있습니다. 되돌릴 근거가 남습니다.
*못 버는 것*: 작정한 조작은 못 막습니다. 이건 방어가 아니라 CCTV입니다.

### 1단계 — 뽑기를 서버로 ✅ 완료
- Edge Function(`supabase/functions/draw-pack`)이 팩을 엽니다. 난수는
  `crypto.getRandomValues`이고, 확률 로직은 `lib/gacha.ts`를 번들한
  `shared.js`를 씁니다 — **확률이 한 벌뿐입니다.**
- 클라이언트 폴백을 제거했습니다. 서버가 응답하지 않으면 뽑기는 실패합니다.
  조용히 브라우저로 돌아가면 그게 곧 서버를 우회하는 길이기 때문입니다.
  (서버가 아예 설정되지 않은 빌드는 계정도 경제도 없으므로 예외입니다.)
- `commit_pull`은 **service_role만** 부를 수 있습니다. 클라이언트가 부를 수
  있으면 원하는 카드를 넣어 달라고 할 수 있습니다.
- 모든 뽑기가 `pull_log`에 남습니다 — 시드, **그때 적용된 확률표**, 천장 전후,
  나온 카드. 표를 나중에 바꿔도 과거 판정을 설명할 수 있어야 하기 때문입니다.
- 픽업 주간이 기기 시간이 아니라 고정 오프셋(KST)으로 정해집니다. 픽업은
  확률을 두 배로 만들므로, 기기 시계로 유리한 주를 고를 수 있으면 안 됩니다.

*왜 먼저인가*: 한국은 2024년 3월부터 확률형 아이템 확률 표시가 법적 의무입니다
(게임산업법 개정). 표시한 확률이 실제와 같음을 **증명할 수 있어야** 하는데,
난수가 브라우저에 있으면 증명할 방법이 없습니다. 상용화 전 필수 조건입니다.
정확한 적용 범위와 표시 방식은 시행 시점 기준으로 법률 검토를 받으시기 바랍니다.

### 2단계 — 골드를 원장(ledger)으로 ◐ 절반
- `gold` 숫자 하나를 지우고 **추가만 되는 거래 기록**으로 바꿉니다.
  잔액은 저장하는 값이 아니라 합계입니다.
  ```
  gold_ledger(user_id, delta, reason, ref_id, created_at)
  잔액 = sum(delta)
  ```
- 모든 획득·소비가 한 줄씩 남습니다. 결제·환불·보상 지급이 전부 추적됩니다.

**지금까지 된 것**: 원장이 골드의 단일 진실이 되었습니다. 뽑기는 서버가
`pull` 사유로 직접 차감합니다. 경기 보상처럼 아직 클라이언트가 계산하는 변동은
`put_save`가 차액을 `client` 사유로 남기므로, **모든 골드 움직임이 이미 한 줄씩
기록됩니다.**

**남은 것**: 그 `client` 줄을 서버가 계산한 사유로 하나씩 바꾸는 일입니다.
3단계(경기 판정 서버화)가 끝나면 경기 보상이 `match`가 되고, 이적시장·합성도
같은 방식으로 옮깁니다. 그때까지 `client` 줄은 "아직 서버가 검증하지 않은
변동"이라는 뜻이며, 감사에서 그대로 눈에 띕니다.

*왜 원장인가*: 돈이 걸리면 "지금 얼마인가"보다 **"왜 그 금액인가"**가 중요해집니다.
잔액만 있으면 분쟁이 났을 때 설명할 수가 없습니다.

### 3단계 — 경기 판정을 서버로
- 클라이언트가 스쿼드와 전술을 **제출**하고, 서버가 시드를 발급해 경기를 돌립니다.
- 서버는 소유하지 않은 카드, 부상 선수, 11명 미달을 거부합니다.
- 결과와 시드를 저장하고, 클라이언트는 같은 시드로 재생만 합니다.
- 3절의 이점 덕분에 엔진 코드를 공유합니다.

### 4단계 — 실시간 리그
- 라운드 시간은 **서버 시계**로만 판정합니다. 기기 시간은 표시용입니다.
- 개입은 "언제 무엇을 지시했다"를 서버가 접수하고, 서버가 그 시점에 반영합니다.
- 개입 보상 골드는 서버가 접수 시각을 근거로 지급합니다.

*ROADMAP 2항이 여기에 해당합니다.* 이미 그 문서에 "서버 시간 기준으로 판정해야
한다"고 적혀 있습니다. 3단계가 끝나야 안전하게 만들 수 있습니다.

### 5단계 — 결제
- 클라이언트가 "결제했다"고 말하는 것을 **절대** 믿지 않습니다.
- PG사 웹훅 → 서버 검증 → 원장에 기록. 이 순서 외의 경로는 없습니다.
- 영수증 재사용(replay) 방지, 멱등 키 필수.
- 청소년 결제 한도, 청약 철회 등은 별도 법률 검토 대상입니다.

## 5. 지금 지켜야 할 규칙

이전이 끝나기 전에도 새 기능은 이 규칙으로 만듭니다.

1. **새 필드는 부류를 정하고 만든다.** A/B 부류이면 서버 소유를 전제로 설계합니다.
2. **클라이언트 계산에 폴백을 두지 않는다.** 서버가 판정하기로 한 것은 서버가
   죽으면 실패해야 합니다. 조용히 로컬로 넘어가면 그게 곧 우회로입니다.
3. **난수는 시드를 기록한다.** 지금도 엔진은 시드를 받습니다. 그 시드를 버리지
   않고 남기면 나중에 서버 판정으로 옮길 때 그대로 쓸 수 있습니다.
4. **클라이언트 암호화·난독화는 대책이 아니다.** 복호화 키가 앱과 함께 배포되므로
   시간만 조금 벌 뿐입니다. 여기에 공수를 쓰지 않습니다.
5. **service_role 키는 브라우저에 절대 닿지 않는다.** 서버 함수 안에서만 씁니다.

## 6. 지금 안전한 것 (오해 방지)

| 항목 | 상태 |
| --- | --- |
| 다른 사람 세이브 | RLS가 `auth.uid() = user_id`로 격리 |
| 비밀번호 | Supabase Auth가 처리, 게임 코드는 접근하지 않음 |
| 번들 속 키 | 공개용 anon 키뿐. service_role 없음 |
| 공지 발행 | 서버의 `is_admin()`이 판정. 화면 숨김이 아님 |
| 깨진 세이브 | `normalizeSave`가 복구, 실패 시 `app/error.tsx` |

취약한 것은 **본인 자산의 자기 조작** 하나이며, 위 단계들이 그것을 없앱니다.

## 7. 모니터링 — 한 가지 신호를 믿지 않는다

조작을 검사 하나로 잡으려 하면, 그 검사를 피하는 방법 하나만 알면 전부 통과합니다.
그래서 서로 다른 층에서 독립적으로 신호를 만들고, **겹치는 계정을 위로 올립니다.**

| 신호 | 무엇을 보는가 | 왜 |
| --- | --- | --- |
| `reject` | 서버가 거부한 저장 | 서버가 이미 "불가능한 상태"라고 판정한 것 |
| `write_rate` | 1시간 저장 240회 초과 | 사람 손으로는 나오지 않는 빈도. 자동화 흔적 |
| `gold_rate` | 시간당 골드 증가 이상치 | 절대 기준이 아니라 또래 대비 |
| `match_rate` | 시간당 경기 수 이상치 | 매크로로 미니게임을 돌리는 패턴 |
| `rollback` | 전적이 줄어든 저장 | 보상만 챙기고 되감는 수법의 흔적 |
| `spam` | 1시간 글 20개 초과 | 조작과 별개로 서비스를 해침 |

**위험도 판정**(`lib/monitor.ts`):
- 평범한 신호 하나 → 낮음. 통신 재시도나 기기 시계 오차로도 걸릴 수 있습니다.
- 저장 거부 하나 → 중간. 서버가 이미 불가능하다고 판정했습니다.
- 서로 다른 신호 둘 → 중간, 셋 → 높음. 거부 + 다른 신호 → 높음.

**조치 전에 반드시 `save_audit`에서 그 계정의 흐름을 직접 봅니다.** 목록은 어디를
볼지 알려줄 뿐이고, 판단을 대신하지 않습니다.

모두 뷰로 만들었으므로 원본 기록은 그대로입니다. 규칙을 나중에 고쳐도 과거
데이터를 다시 볼 수 있습니다.

### 아직 없는 것

지금 신호는 전부 **게임 데이터 안에서만** 나옵니다. 상용화 단계에서는 다음이
더 필요합니다. 지금 넣지 않은 이유는 개인정보 수집 범위를 먼저 정해야 하기
때문입니다.

- **IP·기기 지문**: 다중 계정, 계정 거래, 지역 우회 탐지. 개인정보 처리방침에
  수집 항목으로 명시해야 합니다.
- **인증 이상**: 로그인 실패 폭주, 짧은 시간의 다지역 로그인. Supabase Auth
  로그를 끌어와야 합니다.
- **결제 이상**: 환불 반복, 카드 다수 사용, 칩백(chargeback) 이력.
- **외부 알림**: 지금은 운영자가 화면을 열어야 봅니다. 위험 높음이 뜨면
  메일이나 메신저로 밀어주는 경로가 필요합니다.
