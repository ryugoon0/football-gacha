======================================================================

이 문서는 과거 NHN의 축구 시뮬레이션 게임 '풋볼데이'의 구조를 참고하여,
현재 개발 중인 풋볼데이 유사 축구 시뮬레이션 게임의 방향과 구현 항목을
Claude Code가 이해할 수 있도록 정리한 개발 전달 문서다.

주의:
- 사용자가 제공한 나무위키 URL은 자동 열람 환경에서 직접 접근이 차단되었다.
- 따라서 검색으로 확인되는 나무위키 문서 정보와 당시 공식 보도자료,

- 확인된 사실과 신규 게임을 위한 설계 제안을 구분해서 작성했다.
- 원작의 명칭, UI, 카드 이미지, 데이터, 밸런스 수치를 그대로 복제하지 않는다.
- 실제 선수·클럽·리그 명칭과 사진 사용에는 별도의 라이선스 검토가 필요하다.

1. 풋볼데이의 핵심 정체성
======================================================================

[확인된 내용]

풋볼데이는 액션 축구 게임이 아니라 감독·구단 운영 중심의 웹 기반 축구
시뮬레이션 게임이었다. 핵심 재미는 다음 순환 구조에서 발생했다.

1) 선수 카드를 획득한다.
2) 선수의 소속, 국적, 리그, 능력, 포지션을 고려해 스쿼드를 구성한다.
3) 팀컬러와 케미스트리를 맞춰 선수 개인 능력의 단순 합보다 강한 팀을 만든다.
4) 정해진 시간에 자동으로 진행되는 리그 경기를 확인한다.
5) 경기 중 포메이션, 운영전술, 선수 교체 등에 실시간으로 개입한다.
6) 경기 결과로 순위, 승격, 강등, 컵대회 성적과 보상을 얻는다.
7) 보상으로 다시 선수 영입과 육성을 진행한다.

한 문장 정의:
"수집형 선수 카드와 시간제 리그 운영을 결합하고, 경기 중 감독의 제한된
개입이 결과에 영향을 주는 멀티플랫폼 축구 감독 시뮬레이션"

[신규 게임 설계 방향]

원작의 접근성과 수집 재미는 계승하되, 경기 결과가 단순 팀 전력 숫자와
일회성 능력치 보너스로 결정되지 않도록 한다. 선수 능력, 역할, 공간,
전술 상성, 체력, 경기 흐름이 서로 연결되는 설명 가능한 시뮬레이션을 목표로 한다.

2. 확인된 주요 게임 시스템
======================================================================

2.1 선수 카드와 수집

[확인된 내용]
- 선수 카드 수집이 핵심 콘텐츠였다.
- 노말 카드와 골드 카드가 존재했다.
- 실제 경기에서 좋은 활약을 한 선수를 반영하는 기간 한정 라이브 카드가 있었다.
- 카드 등급에 따라 시작 레벨과 최대 성장 한계가 달랐다.
- 일부 노말 카드는 같은 선수 카드를 재료로 사용해 잠재력 돌파가 가능했다.
- 실제 이적시장 결과가 로스터 업데이트에 반영됐다.

[신규 게임 적용 제안]
- PlayerIdentity와 PlayerCard를 분리한다.
- PlayerIdentity는 실제 또는 가상 선수의 불변 정체성이다.
- PlayerCard는 시즌, 버전, 희귀도, 폼, 성장 한계를 가진 소유 객체다.
- 같은 선수의 여러 시즌 카드는 존재할 수 있지만 한 라인업 중복 출전은 금지한다.
- 라이브 카드는 영구적인 최상위 카드가 아니라 최근 폼과 특정 역할을 표현한다.
- 중복 카드는 단순 소모만 강제하지 말고 돌파, 거래, 교환, 스카우팅 포인트 등
  여러 사용처를 제공한다.

권장 데이터 개념:
- playerId
- cardId
- seasonId
- rarity
- preferredPositions
- preferredFoot
- attributes
- traits
- playStyles
- currentForm
- condition
- fatigue
- potential
- developmentStage
- clubId, leagueId, nationId

2.2 선수 육성

[확인된 내용]
- 훈련과 파트너 훈련으로 선수를 성장시켰다.
- 카드 종류와 초기 등급에 따라 최대 레벨이 달랐다.
- 동일 카드 투입을 통한 잠재력 돌파가 존재했다.
- 후기에는 플레이스타일에 따라 세부 능력치를 재분배하는 성장 기능도 있었다.
- 리그별 라인업 레벨 제한 때문에 최고 등급 선수만 채우는 방식에 제약이 있었다.

[신규 게임 적용 제안]
- 레벨 상승을 모든 능력치의 균등 증가로 구현하지 않는다.
- 나이, 잠재력, 포지션, 훈련 유형, 출전 시간, 코칭 수준에 따라 성장 곡선을 만든다.
- 플레이스타일 선택은 능력치 총합 증가가 아니라 분배와 행동 성향에 영향을 준다.
- 리그 진입 제한을 단순 레벨 합 제한으로 두기보다는 샐러리캡 또는 스쿼드 코스트와
  병행해 다양한 카드가 계속 사용되도록 한다.
- 성장 결과에는 작은 확률 변동을 허용하되, 사용자가 예상 범위를 확인할 수 있어야 한다.

2.3 팀컬러와 케미스트리

[확인된 내용]
- 팀컬러와 케미스트리가 핵심 스쿼드 구성 시스템이었다.
- 동일 클럽, 동일 리그, 동일 국적, 특정 연령, 신체조건, 능력치 조건 등으로 발동했다.
- 한 팀에 장착 가능한 팀컬러 수가 제한됐다.
- 달성하기 어려운 조건일수록 강한 효과가 제공됐다.
- 단순히 높은 등급 선수를 섞는 것보다 조건을 맞춘 스쿼드가 강해질 수 있었다.

[신규 게임 적용 제안]
- 팀컬러는 수집 동기를 제공하되 모든 능력치 일괄 증가를 최소화한다.
- 케미스트리는 전술 수행 안정성, 패스 타이밍, 커버 판단, 압박 연계처럼
  팀 단위 행동의 품질에 영향을 주게 한다.
- 동일 클럽 보너스는 강하지만 특정 덱을 강제하지 않도록 소프트캡을 적용한다.
- 감독 전술 숙련도와 선수 역할 적합도를 케미스트리와 분리한다.

권장 분리 모델:
- familiarity: 함께 뛴 시간과 전술 숙련도
- relationship: 인접 선수 간 연계
- identityBonus: 클럽·리그·국적 기반 수집 보너스
- roleFit: 선수가 맡은 역할과 능력의 적합도
- tacticalCohesion: 전체 포메이션의 간격과 움직임 동기화

팀컬러 효과 예시:
- 같은 아카데미 출신: 압박 연계와 짧은 패스 판단 소폭 증가
- 같은 리그 경험: 전술 적응 속도 증가
- 같은 국가 경험: 초반 조직력 보정
- 장신 스쿼드: 공중볼 경합은 증가하지만 민첩성과 전환 속도에 상쇄 요소 적용
- 젊은 스쿼드: 활동량과 성장률은 높지만 판단 안정성은 낮을 수 있음

2.4 정규리그와 승강제

[확인된 내용]
- 정규리그는 일주일 단위로 운영됐다.
- 같은 그룹에 배정된 이용자들이 반복 경기하여 승점으로 순위를 정했다.
- 승리 3점, 무승부 1점, 패배 0점 구조였다.
- 동률 시 득실차, 다득점, 다승, 승자승 등의 순위 기준이 존재했다.
- 루키부터 최상위까지 여러 단계의 리그가 있었다.
- 자동 승격, 승격 플레이오프, 잔류, 강등 구조가 있었다.
- 정규리그와 별도의 리그컵도 운영됐다.

[신규 게임 적용 제안]
- 시즌 길이는 초기 MVP에서 7일 또는 14일로 설정 가능하게 만든다.
- 서버 스케줄러가 경기 이벤트를 생성하되, 개발 단계에서는 시간을 압축할 수 있어야 한다.
- 사용자 부재 중에도 경기는 진행되며 사전 전술과 자동 교체 규칙이 사용된다.
- 실시간 접속 사용자는 제한된 횟수 또는 쿨다운 안에서 직접 개입할 수 있다.
- 시즌 종료 작업은 순위 확정, 보상, 승강, 다음 시즌 매칭을 원자적으로 처리한다.
- 실제 시간 의존 로직과 경기 시뮬레이션 로직을 분리해 테스트 가능하게 한다.

필요 엔티티:
- Competition
- Season
- LeagueTier
- LeagueGroup
- Fixture
- Standing
- PromotionRule
- CupBracket
- SeasonReward

2.5 경기 콘텐츠

[확인된 내용]
- 정규리그
- 리그컵
- 실제 유명 클럽 콘셉트의 AI 팀과 겨루는 월드투어
- 특정 테마의 AI 팀과 매일 경기하는 데일리매치
- 친구 또는 다른 이용자와 겨루는 PvP 친선경기
- 친선경기에서도 선수 교체와 포메이션 변경이 가능했다.

[신규 게임 적용 제안]
- MVP는 AI 친선경기와 소규모 비동기 리그부터 구현한다.
- 월드투어는 전술 튜토리얼 역할도 담당하게 한다.
- 예: 강한 측면 공격 팀, 깊은 수비 블록 팀, 높은 압박 팀을 차례로 상대한다.
- 데일리매치는 매일 다른 전술 문제를 제시하고 보상과 학습 효과를 제공한다.
- PvP는 완전 실시간 통신보다 동일한 시뮬레이션 서버에서 전술 명령만 동기화하는
  준실시간 구조를 먼저 고려한다.

3. 전술 시스템 상세 분석
======================================================================

3.1 원작에서 확인되는 전술 입력

- 포메이션
- 공격 방향: 중앙, 좌측, 우측, 양쪽 등
- 태클 강도
- 중거리 슛 성향
- 패스 유형: 짧게 또는 길게
- 공수 밸런스
- 교체전술: 낮은 평점, 낮은 체력, 부상 등을 조건으로 교체
- 선수지정: 특정 역할 담당자 설정
- 작전카드: 경기마다 부족한 능력을 일시 보완
- 경기 중 포메이션 변경과 선수 교체

3.2 원작 구조의 장점

- 축구 지식이 많지 않아도 이해하기 쉽다.
- 선택지가 적어서 모바일에서도 빠르게 조작할 수 있다.
- 경기 중 개입 결과를 바로 관찰할 수 있다.
- 카드 수집, 선수 능력과 전술 설정이 직접 연결된다.
- 사전 자동 교체 설정으로 접속하지 못한 사용자도 대응할 수 있다.

3.3 원작 구조를 그대로 복제할 때의 문제

- 전술이 능력치 보너스 선택으로 축소될 위험이 있다.
- 높은 등급 카드와 팀컬러의 숫자 합이 경기 결과를 지나치게 지배할 수 있다.
- 중앙/측면, 짧게/길게 같은 이분법만으로 실제 축구의 공간 상호작용을 표현하기 어렵다.
- 작전카드가 과금형 일회성 능력치 버프가 되면 공정성과 전술성이 훼손될 수 있다.
- 명목상 다양한 포메이션이 존재해도 특정 메타 포메이션만 남을 수 있다.

3.4 신규 게임의 전술 입력 모델

사용자에게는 단순하게 보이되 내부 엔진에서는 연속값으로 변환한다.

A. 기본 형태
- baseFormation
- inPossessionShape
- outOfPossessionShape
- defensiveLineHeight: 0~100
- teamWidth: 0~100
- compactness: 0~100

B. 점유 시
- buildUpStyle: short / balanced / direct
- buildUpRisk: 0~100
- tempo: 0~100
- passingDirectness: 0~100
- attackingWidth: 0~100
- overlapBias: 0~100
- crossingFrequency: 0~100
- longShotFrequency: 0~100
- finalThirdRisk: 0~100

C. 비점유 시
- pressingIntensity: 0~100
- pressingTrigger: passive / badTouch / wide / backwardPass / always
- defensiveBlock: low / mid / high
- markingStyle: zonal / mixed / manOriented
- tackleIntensity: 0~100
- counterPressDuration: 0~10 seconds

D. 전환
- onWinPossession: retain / balanced / counter
- onLosePossession: regroup / counterPress
- goalkeeperDistribution: short / mixed / long

E. 개인 역할
- role
- duty: defend / support / attack
- roam
- pressMore
- takeMoreRisks
- holdPosition
- overlapOrUnderlap

3.5 전술 효과 계산 원칙

전술 설정이 곧바로 능력치에 +N을 주는 구조를 피한다.
전술은 선수의 행동 선택 확률, 위치, 이동 목표, 체력 소비에 영향을 준다.

예시:
- 높은 압박은 전방 탈취 확률을 높이지만 체력 소모와 배후 공간 위험을 증가시킨다.
- 높은 수비라인은 팀 간격을 줄이지만 빠른 공격수에게 침투 공간을 내줄 수 있다.
- 짧은 패스는 기술과 판단이 좋은 팀에서 점유 안정성을 높이지만 강한 압박에 갇힐 수 있다.
- 직접 패스는 전진 속도를 높이지만 볼 소유권 상실 확률도 높인다.
- 넓은 공격 폭은 측면 공간을 만들지만 중앙 전환 수비가 약해질 수 있다.
- 강한 태클은 탈취 확률과 함께 파울, 카드, 부상 위험을 올린다.

행동 성공 확률의 기본 형태:

successProbability = sigmoid(
    playerSkillComponent
  + tacticalFitComponent
  + spatialAdvantageComponent
  + teammateSupportComponent
  - opponentPressureComponent
  - fatiguePenalty
  - conditionPenalty
  + boundedRandomness
)

필수 원칙:
- 모든 보정값은 단일 함수에 하드코딩하지 않는다.
- 각 보정값의 기여도를 경기 로그에서 추적할 수 있게 한다.
- 무작위성은 존재하지만 강팀과 좋은 선택의 누적 우위를 훼손하지 않을 범위로 제한한다.
- 동일 seed와 동일 입력이면 같은 경기 결과를 재현할 수 있어야 한다.

3.6 전술 상성은 고정 가위바위보로 만들지 않는다

잘못된 예:
- 4-3-3은 무조건 4-4-2에 +10%
- 중앙 공격은 측면 수비에 무조건 승리

권장 방식:
- 포메이션 이름이 아니라 실제 생성되는 공간과 수적 관계를 평가한다.
- 각 구역의 선수 수, 거리, 압박 도착 시간, 패스 선택지, 커버 선수를 계산한다.
- 같은 4-3-3도 역할과 지시에 따라 전혀 다른 구조가 되게 한다.
- 상성은 특정 상황과 선수 구성에 따라 자연스럽게 발생해야 한다.

4. 경기 엔진 권장 구조
======================================================================

4.1 계층 분리

Layer 1: Match Orchestrator
- 경기 시작과 종료
- 시간 진행
- 이벤트 큐
- 교체와 전술 명령 수신
- seed 관리

Layer 2: Tactical State
- 현재 포메이션
- 점유/비점유 형태
- 팀 지시
- 선수 역할
- 경기 중 변경 이력

Layer 3: Spatial Model
- 경기장을 구역 또는 좌표로 표현
- 선수 위치와 이동 목표
- 팀 간격과 수적 우위
- 패스 레인과 압박 거리

Layer 4: Decision Engine
- 공 소유자의 패스, 드리블, 슛, 클리어 선택
- 비소유자의 압박, 커버, 마킹, 침투 선택
- 선수 성향과 감독 전술을 함께 반영

Layer 5: Resolution Engine
- 패스, 경합, 태클, 슛 등 행동 결과 계산
- 능력치, 공간, 압박, 체력, 무작위성 반영

Layer 6: Event and Commentary
- 내부 이벤트를 사용자용 중계 문장으로 변환
- 중요한 장면만 하이라이트로 노출
- 디버그용 상세 원인 로그는 별도 보존

4.2 최소 이벤트 종류

- kickoff
- possession_change
- pass_attempt / pass_complete / pass_failed
- progressive_pass
- dribble_attempt / dribble_success / dribble_failed
- pressure
- tackle_attempt / tackle_success / foul
- interception
- cross
- shot / shot_on_target / goal / save / block
- set_piece
- injury
- yellow_card / red_card
- substitution
- tactical_change
- halftime / fulltime

4.3 경기 상태 스냅샷

매 시뮬레이션 tick 전체 상태를 DB에 저장하지 않는다.
메모리에서 처리하고 다음 항목만 선택적으로 보존한다.

- 시작 입력 스냅샷
- randomSeed
- 중요 이벤트 로그
- 전술 변경과 교체 명령
- 하프타임 상태
- 최종 통계와 결과
- 엔진 버전

이 구조를 통해 동일 경기 재현, 버그 조사, 밸런스 비교가 가능해야 한다.

5. 실시간 개입 설계
======================================================================

[원작에서 확인된 핵심]
정해진 시간에 경기가 자동 진행되지만 사용자가 접속하면 선수 교체와 전술 변경으로
개입할 수 있었다. 이것이 풋볼데이의 중요한 차별점이었다.

[신규 게임 권장안]

경기 전:
- 선발과 후보 등록
- 기본 전술 등록
- 상황별 전술 프리셋 등록
- 자동 교체 규칙 등록
- 리드/동점/열세 상황별 대응 규칙 등록

경기 중:
- 선수 교체
- 전술 프리셋 전환
- 공격성, 압박, 라인 높이 등 제한된 핵심 지시 변경
- 부상과 퇴장에 대한 대응

공정성 규칙:
- 접속 사용자가 무조건 유리하지 않도록 사전 자동 지시도 충분히 강력하게 만든다.
- 전술 변경은 즉시 100% 적용하지 않고 선수들의 전술 적응 시간 또는 혼란 비용을 둔다.
- 잦은 전술 변경에 쿨다운 또는 조직력 패널티를 적용한다.
- 서버가 모든 명령의 유효성과 적용 시점을 결정한다.

자동 교체 규칙 예시:
- 부상 발생 시 같은 주포지션의 후보 우선
- 체력 25 이하이며 60분 이후일 때 교체
- 평점이 낮은 공격수를 65분 이후 교체
- 70분 이후 열세이면 수비 역할 선수를 공격 역할 선수로 교체
- 퇴장 시 포메이션 안전 프리셋으로 전환

6. 경제와 수집 설계 시 주의사항
======================================================================

풋볼데이는 카드 수집과 작전카드가 핵심이었지만 신규 게임은 전술 게임이라는 목표를
해치지 않도록 다음 원칙을 적용한다.

- 과금 아이템이 경기 중 직접적인 능력치 우위를 구매하게 하지 않는다.
- 작전카드를 유지한다면 능력치 버프가 아니라 스카우팅, 분석, 훈련 효율 등으로 재해석한다.
- 선수 획득 확률과 천장 구조를 명확히 공개한다.
- 낮은 등급 선수도 팀컬러, 역할 적합도, 성장으로 장기간 활용 가능하게 한다.
- 라이브 카드는 실제 경기 결과를 반영하되 기존 카드의 가치를 즉시 파괴하지 않는다.
- 카드 인플레이션을 억제하기 위해 시즌별 무한 능력치 상승을 피한다.

7. 구현 우선순위
======================================================================

Phase 0: 기존 코드 분석
- 현재 기술 스택, 디렉터리, DB 스키마, 구현된 화면과 API를 확인한다.
- 아래 설계와 기존 구현을 비교해 이미 존재하는 기능을 표시한다.
- 기존 사용자 변경을 보존하고 바로 대규모 수정하지 않는다.

Phase 1: Headless 경기 엔진 MVP
- 두 팀 라인업 입력
- 기본 포메이션과 역할
- 패스, 경합, 슛, 골 이벤트
- 체력과 간단한 전술 보정
- seed 기반 재현
- 최종 결과와 통계

완료 조건:
- UI 없이 자동 테스트로 1,000경기를 실행할 수 있다.
- 같은 seed는 같은 결과를 낸다.
- 홈/원정 팀을 바꿨을 때 편향을 측정할 수 있다.
- 무득점, 대량득점, 퇴장 등 극단값을 검출한다.

Phase 2: 선수·카드·스쿼드
- 선수 원본과 카드 소유 객체 분리
- 포지션 적합도
- 성장과 컨디션
- 라인업 유효성 검사
- 초기 팀컬러와 케미스트리

Phase 3: 전술 엔진
- 점유/비점유 전술
- 역할별 위치와 행동
- 압박, 라인 높이, 폭, 템포, 패스 성향
- 공간과 수적 우위 계산
- 전술 변경 이력

Phase 4: 경기 중계 및 개입
- 중요 이벤트 중계
- WebSocket 또는 SSE 상태 전달
- 전술 프리셋 전환
- 교체와 자동 교체
- 재접속과 중복 명령 처리

Phase 5: 비동기 리그
- 리그 그룹 편성
- 일정 생성
- 순위 계산
- 시즌 마감
- 승격, 플레이오프, 강등
- 보상

Phase 6: 확장 콘텐츠
- 컵대회
- 월드투어형 PvE
- 데일리 전술 도전
- 친선 PvP
- 라이브 카드 및 로스터 업데이트 파이프라인

8. 필수 테스트 전략
======================================================================

단위 테스트:
- 능력치 정규화
- 포지션 적합도
- 팀컬러 조건 판정
- 케미스트리 계산
- 교체 조건 우선순위
- 승점과 동률 순위 계산
- 승격/강등 대상 결정

결정론 테스트:
- 동일 입력과 동일 seed의 이벤트 로그 해시가 동일해야 한다.
- 엔진 버전이 바뀌면 기존 리플레이와 구분되어야 한다.

통계 테스트:
- 동일 전력 팀 간 승률이 장기간 한쪽으로 치우치지 않는다.
- 전력 차이가 커질수록 기대 승률이 단조롭게 증가한다.
- 강한 압박은 탈취 위치와 체력 소모를 함께 증가시킨다.
- 높은 라인은 오프사이드 유도와 배후 침투 허용을 함께 증가시킨다.
- 강한 태클은 탈취와 파울을 함께 증가시킨다.
- 전술 효과가 선수 능력 차이를 완전히 무효화하지 않는다.

속성 기반 테스트:
- 선수는 동시에 두 위치에 존재할 수 없다.
- 퇴장 또는 교체된 선수는 이후 행동 이벤트를 만들 수 없다.
- 득점 합계와 이벤트 로그의 goal 수가 일치한다.
- 소유 시간 합계가 전체 경기 시간을 초과하지 않는다.
- 한 팀의 출전 선수 수가 규칙을 위반하지 않는다.

부하 테스트:
- 목표 동시 경기 수를 정한 뒤 CPU와 메모리를 측정한다.
- 전체 경기 tick 저장으로 DB가 병목되지 않도록 한다.
- 시즌 마감 작업의 중복 실행을 방지한다.

9. 관측성과 밸런싱 도구
======================================================================

경기 엔진은 결과만 반환하지 말고 왜 그런 결과가 나왔는지 분석할 수 있어야 한다.

필수 메트릭:
- 팀별 기대득점 유사 지표
- 슛, 유효슈팅, 박스 안 슛
- 점유율
- 전진 패스와 패스 성공률
- 높은 지역에서의 볼 탈취
- 압박 성공률
- 평균 수비라인 높이
- 팀 폭과 종·횡 간격
- 체력 감소량
- 전술별 승률
- 포메이션과 역할 조합별 사용률/승률
- 카드 등급별 출전률/승률

밸런스 원칙:
- 승률만 보지 말고 사용률과 상대 조합을 함께 본다.
- 강한 전술을 직접 하향하기 전에 그 전술이 강한 공간적 이유를 확인한다.
- 한 번에 여러 계수를 바꾸지 않는다.
- 엔진 버전별 대량 시뮬레이션 결과를 비교한다.
- 밸런스 상수는 코드에서 분리해 버전 관리한다.

10. Claude Code에 대한 실제 작업 지시
======================================================================

아래 순서로 작업하라.

1) 먼저 현재 저장소를 읽고 다음을 보고한다.
- 기술 스택
- 주요 디렉터리
- 현재 구현된 선수, 카드, 스쿼드, 경기, 전술, 리그 기능
- 현재 경기 엔진 진입점
- 테스트 실행 방법
- 이 문서와 충돌하거나 중복되는 기존 설계

2) 아직 코드를 수정하지 말고 Gap Analysis 문서를 작성한다.
- 구현 완료
- 부분 구현
- 미구현
- 리팩터링 필요
- 즉시 수정하면 위험한 영역

3) 다음 산출물을 제안한다.
- 최소 변경 아키텍처
- 신규 또는 수정 대상 파일 목록
- 핵심 타입과 인터페이스
- 단계별 마이그레이션 계획
- 테스트 계획
- 첫 번째 구현 단위

4) 첫 번째 구현 단위는 반드시 작고 검증 가능하게 정한다.
권장 첫 단위:
- seed 기반 Headless MatchEngine
- 두 팀 입력
- 간단한 패스/슛/골 이벤트
- 최종 MatchResult
- 결정론 테스트

5) 다음 제약을 지킨다.
- 사용자의 기존 변경사항을 덮어쓰지 않는다.
- 기존 공개 API를 불필요하게 변경하지 않는다.
- 대규모 구조 변경 전에는 이유와 영향을 먼저 보고한다.
- 전술 상성을 포메이션 이름 기반 고정 보너스로 구현하지 않는다.
- 임시 랜덤 수치를 여러 파일에 하드코딩하지 않는다.
- UI와 시뮬레이션 도메인 로직을 분리한다.
- 시간 스케줄러와 경기 계산을 분리한다.
- DB가 없어도 경기 엔진 단위 테스트를 실행할 수 있게 한다.
- 모든 경기에는 seed와 engineVersion을 기록한다.

6) 결과 보고 형식
- 분석한 파일
- 현재 구조 요약
- 확인된 Gap
- 제안 아키텍처
- 수정할 파일
- 구현 범위
- 테스트 항목
- 남은 위험

11. Claude Code에 바로 입력할 실행 프롬프트
======================================================================

다음 텍스트를 Claude Code에 전달한다.

--- 실행 프롬프트 시작 ---

첨부된 "football-day-claude-code-handoff.txt"를 이 프로젝트의 제품 및 기술
참고 문서로 읽어줘.

이 프로젝트의 최우선 목표는 풋볼데이의 접근성, 카드 수집, 정기 리그,
실시간 감독 개입의 재미를 참고하면서 실제 축구의 전술 작용을 더 충실하게
재현하는 축구 시뮬레이션을 만드는 것이다.

먼저 저장소 전체 구조를 필요한 범위에서만 확인하고 다음을 보고해줘.

1. 현재 기술 스택과 주요 디렉터리
2. 선수/카드/스쿼드/경기/전술/리그 기능의 구현 상태
3. 현재 경기 엔진의 진입점과 데이터 흐름
4. 첨부 문서 기준 Gap Analysis
5. 기존 코드를 최대한 유지하는 단계별 구현 계획
6. 첫 번째로 구현할 수 있는 작고 검증 가능한 작업
7. 수정 예상 파일과 테스트 항목

이번 단계에서는 코드를 수정하지 마. 분석과 계획만 작성해줘.
확인되지 않은 구조를 추측하지 말고 실제 파일을 근거로 답해줘.
대규모 파일 읽기나 불필요한 전체 재분석을 피하고 관련 파일부터 좁혀가며 확인해줘.

복잡한 전술 엔진 설계, 시뮬레이션 계산식, 독립 검토가 필요하면 연동된 Codex에
범위를 좁혀 위임할 수 있다. 단, Claude와 Codex가 같은 작업을 처음부터 중복해서
분석하지 않도록 역할과 대상 파일을 명확히 나눠줘.
